# 검색 데이터 파이프라인 설계 (Charter 부속)

> 방대한 검색 데이터가 ERP 전반에 흩어져 쓰이므로, **단일 창구 하나**로 유기적으로 흐르게 한다.
> 이 문서는 Charter(`geo-studio-charter.md`)의 데이터 정책을 ERP 전역으로 확장한 설계 기준이다.

## 1. 두 데이터의 정의 (혼동 금지)

| | 검색량(Volume) | 트렌드(Trend) |
|---|---|---|
| 값 | 절대 월간 검색수(PC·모바일·합계) | 상대 지수 0~100(최근 6개월) |
| 의미 | **시장 규모·기회 크기** | **관심 추세·타이밍·계절성** |
| 출처 | 검색광고 API(`NAVER_AD_*`) | 데이터랩 API(`NAVER_CLIENT_*`) ✅연동 |
| 원칙 | 규모 판단·우선순위·매출추정에 | 타이밍·모멘텀·성과추적에 |

**둘은 경쟁이 아니라 상보** — 규모(얼마나 크냐) + 타이밍(지금 뜨냐)을 함께 봐야 의사결정이 된다.

## 2. 단일 창구 원칙 (유기적 파이프라인의 핵심)

```
         ┌──────────────── SearchDataPort (단일 계약) ────────────────┐
NAVER ─→ │ searchVolume(트렌드) · monthlyVolume(검색량) · serpTop ...   │
AD    ─→ │   Provider: mock | naver | hybrid  (resolver가 선택)         │
         └───────────────────────────┬────────────────────────────────┘
                                     │  (모든 소비자는 이 한 곳으로)
   ┌───────────────┬─────────────────┼──────────────┬─────────────────┐
 /keywords      거래처인사이트     컨설팅리포트     GEO Studio        캠페인 ROI
```

- **모든 검색 데이터 접근은 `SearchDataPort` 하나를 통한다.** 화면·액션이 `fetchKeywordVolumes`/`fetchKeywordTrends`를 직접 부르지 않는다(현재는 흩어져 있음 → 점진 이관).
- 이점: ① 목↔실측 무중단 스왑 ② 캐시·쿼터·폴백을 한 곳에서 ③ 티어 배지 일관 ④ 신규 화면은 배선만.

## 3. 소비자 지도 (현재 → 목표)

| 카테고리 | 화면/기능 | 검색량 | 트렌드 | 현재 | 목표 |
|---|---|---|---|---|---|
| 영업·계약 | 거래처 상세 | 규모 | 모멘텀 | 량✅/트렌드❌ | 둘 다(백데이터) |
| 영업·계약 | 컨설팅 리포트(고객문서) | 제안 근거 | 타이밍 코멘트 | 량✅/트렌드❌ | 둘 다 |
| 기획·분석 | 거래처 인사이트 | 시장 규모 | 급상승 표시 | 량✅/트렌드❌ | 둘 다 |
| 기획·분석 | 키워드 리서치(`/keywords`) | 검색수 | 추세 | 택1(모드) | **동시 표기** |
| 기획·분석 | GEO CEP(`/geo-cep`) | 카테고리 규모 | 계절성 | 량 카드✅ | +트렌드 스파크라인 |
| 기획·분석 | GEO 캠페인 ROI | 매출 추정 입력 | — | 고정 10만 | 실측 검색량 |
| 보고·기록 | 캠페인 성과(P3) | — | 브랜드 검색지수 | ❌ | 트렌드 시계열 |

### DB 관점 (중요)
`Keyword` 모델에 **`searchVolume`·`trendRatio` 필드가 이미 둘 다 존재**(마이그레이션 완료).
→ 트렌드 백데이터는 **스키마 변경 없이** 컨설팅 생성 시 `trendRatio`를 채우기만 하면 된다(빈칸 채우기).

## 4. 실행 단계 & 경계

| 단계 | 내용 | 경계 |
|---|---|---|
| **S1** | `/geo-cep` 카테고리 카드에 트렌드 스파크라인 추가 → "둘 다" 패턴 확립 | 🟢 geo-* |
| **S2** | GEO 캠페인 ROI에 실측 검색량 배선 | 🟢 geo-* |
| **S3** | 컨설팅 생성 시 `trendRatio` 채움 → 거래처·인사이트에 트렌드 백데이터 | 🟡 기존 화면(additive, 무스키마) |
| **S4** | `/keywords` → "키워드 리서치"(검색량+트렌드 동시) 재편 + 이름 정직화 | 🟡 기존 화면 |
| **S5** | 흩어진 직접 호출(consulting/keywords)을 `SearchDataPort`로 이관 | 🟡 리팩터 |
| **S6a** | 브랜드 검색지수 = 시계열 **라이브** 비교(브랜드·카테고리·경쟁사, 과거비교) | 🟢 무스키마(데이터랩 실시간) ✅ |
| **S6b** | 시계열 **스냅샷 저장**(TrendSnapshot·조회 시점 지수 이력) | ✅ additive schema |

- 🟢 = 즉시(무충돌). 🟡 = 기존 ERP 공유 → additive·소규모로 신중히. 🔴 = 스키마 조율.
- 모든 단계: 티어 배지 필수, `schema.prisma` 변경 금지(S6b 제외), 테스트·스크린샷 검증.

### P3 결정 — 스키마 없이 먼저 라이브(S6a)

데이터랩이 **요청마다 6개월 시계열을 반환**하므로 시계열·과거비교·브랜드검색지수는
저장 없이 즉시 산출 가능. `buildBrandTrendIndex(provider, {brand,category,competitors})`가
`SearchDataPort.searchVolume`만 사용 → 하이브리드 폴백·effectiveTier 배지 그대로 적용.
장기 추세(작년 동월 대비 등) 저장이 필요해질 때만 S6b로 스냅샷 스키마를 조율한다.
`/geo-cep`에 **브랜드 검색지수·시계열 비교** 패널(다중 라인 + 과거비교 표)로 노출.
