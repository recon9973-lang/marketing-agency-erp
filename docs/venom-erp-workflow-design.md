# VENOM ERP — 워크플로우 상세 설계서
> 병원 광고대행사 Marketing OS · 이상 청사진 + 현재 갭 + 전환 로드맵
> 작성: 2026-07-19 · 대상 브랜치 `erp-v1` · 상태: 살아있는 설계 문서(living spec)

이 문서는 **전수조사**(저장소 설계 문서군 + 코드 모듈 인벤토리 + 대화 맥락)를 근거로,
"실제 업무 흐름대로 굴러가는 ERP"를 만들기 위한 설계를 **분석 → 브레인스토밍 → 기획** 순서로 정리한다.

핵심 문제의식(사장님): *"현재 ERP는 껍데기만 있고 실제 사용하기 어려운 구조."*
핵심 진단: **기능이 없어서가 아니라, 8단계 업무 흐름을 하나로 꿰는 뼈대(레일)가 없어 각 모듈이 따로 논다.**

---

## 0. 배경·목적·범위 (Executive Summary)

- **무엇:** ㈜베놈(병원·의원 특화 마케팅 대행사)의 **단일 기록시스템(System of Record)**. 자사 WordPress와 분리된 별도 웹앱(`erp.seokorea.org`). Next.js 15 + Prisma + Neon.
- **누구:** 내부 3역할(**최고관리자 · 관리자 · 마케터**) + **거래처(병원)는 로그인 없이 토큰 페이지**(포털·서명·설문·결제).
- **왜:** 흩어진 도구(NAS 팀앱·Airtable·스프레드시트)를 대체하고 **계약→설문→콘텐츠→보고서 흐름에서 재입력 0**, **의료법 검수 게이트**, 청구·정산·감사를 하나로.
- **목표 지표:** 담당자당 관리 병원 4~6 → **8~12**, 온보딩 2주 → **3일**.
- **이 문서의 범위:** 8단계 업무 워크플로우를 레일로 통합하는 **목표 구조 + 데이터 인계 계약 + 단계별 상세 설계 + 현재 갭 + 전환 로드맵 + 미결 질문**.

### 표준 업무 8단계 (사장님 정의)
```
1. 상담문의 → 2. 자료수집·분석·컨설팅보고서 → 3. 보고서전달·미팅 → 4. 계약
   → 5. 담당자배정 → 6. 키워드수집 → 7. GEO측정 → 8. 콘텐츠생성 → (운영·보고·정산)
```

## 1. 분석 (Analysis)

### 1.1 현황 성숙도 — "튼튼한 몸통 + 목(mock) 지능층"
전수조사 결과, VENOM ERP는 **60여 Prisma 모델·50+ 기능 화면**을 가진 넓은 시스템이며, 성숙도는 두 층으로 갈린다.

- **REAL 몸통(실 DB로 동작):** 리드·계약·거래처·업무·재무·보고서·보관함·포털·권한 — 서버액션+Zod로 실제 데이터 위에서 완전 동작.
- **CONNECTED-MOCK 지능층("키 넣으면 켜짐"):** AI 콘텐츠(Anthropic/OpenAI), 키워드 검색량·순위(네이버), GEO 분석(mock 프로바이더 폴백), 구글 GSC/GA4, 토스 결제, 워드프레스 발행 — **끝까지 동작하되 키 없으면 데모/추정으로 정직하게 강등**. 이건 의도된 잘 라벨된 패턴(데모 배지·TierBadge)이지 미완성 허상이 아니다.

> 정직성 레이어(`src/server/integrations/status.ts`)가 24개 연동의 설정 상태·폴백을 단일 진실로 선언하고, 심지어 캘린더 동기화는 코드가 없으므로 `configured:false`로 **정직하게 미연결 표시**. 이 자기보고 정직성이 이 시스템의 강점.

### 1.2 8단계 현재 매핑 (구현 위치 · 성숙도 · 끊김)

| # | 단계 | 구현 모듈 | 성숙도 | 데이터 연결/끊김 |
|---|---|---|---|---|
| 1 | 상담문의 | 리드 CRM `/leads` (`Lead`) | **REAL** | Lead 레코드, 중복검사·동의수집 |
| 2 | 자료수집·컨설팅보고서 | 무료 SEO진단(Lead) + 컨설팅리포트(Client) | **MOCK연결** | ⚠️ **컨설팅이 Client에만 묶임(leadId 없음)** → 계약 전 생성 불가(순서 역전) |
| 3 | 보고서전달·미팅 | 견적 `Quote` + 회의록 `/meetings` + 포털전달 | REAL/MOCK | 견적은 leadId 연결, 미팅은 자유부동 |
| 4 | 계약 | 계약서+원격서명 `/contracts`,`/sign` | **REAL** | ✅ 서명 시 업무 자동생성(강한 이음새) |
| 5 | 담당자배정 | 리드→거래처 전환 + 마케터 배정 | **REAL** | ✅ 전환 트랜잭션서 원자적 배정(가장 튼튼) |
| 6 | 키워드수집 | 키워드관리+월보장+검색량 | **MOCK연결** | 저장 REAL, 검색량·연관어는 네이버 키 필요 |
| 7 | GEO측정 | GEO모니터링 `/geo` + GEO Studio(M1~M5) | **MOCK연결** | 수동관측 REAL, 자동은 AI키·mock 폴백 |
| 8 | 콘텐츠생성 | 원고·이미지·디자인·AI스튜디오+답변페이지+검수 | **MOCK연결** | 생성 AI키 필요, 검수 REAL, 포털컨펌 REAL |

### 1.3 핵심 문제 (왜 "껍데기"로 느껴지나)

1. **모듈 간 파이프라인 강제가 없음.** `Lead.status`·`Client.stage`는 자유 문자열이고 전이 로직은 `domain/` 헬퍼에만 있어 **순서를 강제하지 않는다.** 계약 안 한 거래처에도 콘텐츠를 만들 수 있음. → *"레일이 없다."*
2. **데이터 인계 이음새 결손.** 계약서에서 기존 거래처를 골라도 갑 정보가 빈칸(→ 최근 수정), 컨설팅이 Client에만 묶여 리드 단계서 못 만듦 등, **한 번 넣은 정보가 다음 단계로 안 흐른다.**
3. **GEO가 7개 형제 라우트로 파편화**(`/geo`, `/geo-studio`, `/geo-scan`, `/geo-cep`, `/journeymap(구 geo-path)`, `/geo-planner`, `/geo-content`) — 같은 데이터층을 쓰지만 **병렬 도구로 흩어져** 하나의 흐름으로 안 보임. "toolbox 느낌"의 최대 원인.
4. **자동화 스캐폴드가 선언만 되고 배선 안 됨.** `Product.defaultTasks/defaultSurveyQuestions/defaultReportMetrics`가 "계약→업무·설문·보고서 자동생성"을 약속하지만 하류 생성이 PARTIAL.
5. **크론 의존 신선도.** 일일 순위·GEO·인사이트 갱신이 `CRON_SECRET`에 게이트 → 없으면 "실측" 데이터가 조용히 멈춤.

### 1.4 강점(재사용할 자산)
- 정직성 레이어(단일 연동 레지스트리) · REAL CRUD 몸통 · **FK 사슬은 이미 존재**(Lead→Client→Contract→Keyword→GeoQuestion→ContentPlan) · GEO 골든테스트 엔지니어링 · 병원 SoT(HospitalProfile) · 권한 스코프(AccessScope) · 토큰 포털 보안경계.

> **결론:** 연결 조직(모델·전환액션·`answerPlanId` 브리지·포털 컨펌 루프)은 **이미 있다.** 없는 것은 *그 위를 굴러가게 하는 오케스트레이션(레일)*. → 새로 만들기보다 **배선**이 대부분.

## 2. 브레인스토밍 (Brainstorming)

### 2.1 계승할 설계 원칙 (문서군에서 확정된 것)
1. **SoT + 근거표시:** `HospitalProfile`이 축. 모든 AI 산출물은 근거(sourceRefs) 표시. **재입력 0.**
2. **정직성 티어링:** 🟢실측 / 🟡데모(배지) / ⚪미연결(숨김+안내). 의사결정·고객문서에 쓰이는 수치는 🟡 대신 ⚪로. 하이브리드 폴백은 실제 쓰인 티어로 배지 강등.
3. **사람 승인형 반자동:** AI는 **표시자이지 판단자 아님**. 계약확정·의료법통과·고객발송·지출승인은 사람 최종서명.
4. **비파괴 추가 스키마:** 필드 추가만, expand→backfill→contract 3단계. `prisma db push` 비파괴.
5. **"키 넣으면 켜짐":** 연동은 스텁+수동폴백, env 추가 시 실경로 자동 활성. 새 소스 = 레지스트리 1줄.
6. **의료법 하드 게이트:** §56 14개 금지유형 → `ComplianceCheck.riskFlags`, §57 사전심의. 규칙엔진 1차 → Claude 2차 → 사람 최종. 승인 없이는 PUBLISHED 불가.
7. **KST/UTC:** 저장 UTC + 사용자 timezone(기본 Asia/Seoul).

### 2.2 핵심 아이디어 — "레일 + 인계 계약 + 통합 워크스페이스"

**아이디어 A — 단일 파이프라인 레일 (채택·진행중).**
리드(1~4단계, `Lead.status`) → 계약 전환 → 거래처(5~8단계, `Client.stage`)로 **하나의 상태 축**을 잇는다. 각 거래처가 "지금 몇 단계, 다음 할 일 무엇"을 항상 안다. *(Phase 1에서 `Client.stage` 백본 이미 구축.)*

**아이디어 B — 데이터 인계 계약(Carry-Forward Contract).**
"업체명·컨설팅 자료·계약 정보"가 한 번 입력되면 다음 단계서 **재입력 없이 자동 인계**. 각 필드가 *어디서 생성 → 어디서 재사용*되는지 명시적 계약으로 정의(→ §3.3). *(계약 이음새 양방향 인계 이미 구현.)*

**아이디어 C — GEO 통합 워크스페이스.**
7개 GEO 라우트를 **하나의 거래처-스코프 GEO 워크스페이스**로 묶어 스캔→CEP→여정→콘텐츠→플랜을 한 흐름으로. (라우트는 유지하되 진입점·컨텍스트를 거래처 단계에 종속.)

**아이디어 D — 이벤트 기반 단계 자동전환.**
도메인 이벤트로 단계 자동 진행: 계약체결→배정, 키워드확정→키워드완료, GEO질문승인→GEO, 콘텐츠발행→운영. `GeoQuestion.answerPlanId`(잠재 링크) 활성화로 7→8 자동 인계.

**아이디어 E — 가시성 화면.**
거래처 **칸반 보드**(단계별 칸) + 거래처 **여정 타임라인**(상담→…→콘텐츠 시간순 한 화면). 흩어진 탭을 흐름으로.

### 2.3 대안 비교(요약)
| 관점 | 택1 | 왜 |
|---|---|---|
| 상태 저장 | Prisma enum vs **String+도메인 유니온** | 기존 `Lead.status` 규약 일치 → String 채택 |
| GEO 통합 | 라우트 통폐합 vs **진입점·컨텍스트만 거래처 종속** | 골든테스트·기존 URL 보존 위해 후자 |
| 자동전환 | 완전자동 vs **이벤트 제안+사람 확인** | 원칙3(사람 승인형)에 맞춰 반자동 |
| 컨설팅 위치 | Client 전용 유지 vs **leadId 추가(계약 전 생성)** | 실제 순서(보고서→계약)에 맞춰 후자 |

## 3. 기획 (Detailed Design)

### 3.1 목표 아키텍처 (Ideal Blueprint)

```
        [리드 파이프라인]                         [거래처 파이프라인]
  NEW→CONTACTING→AUDIT→MEETING→PROPOSAL ──계약전환──▶ ONBOARDING→KEYWORD→GEO→CONTENT→LIVE
     (1.상담  2.진단·보고서  3.미팅   4.계약)          (5.배정  6.키워드  7.GEO  8.콘텐츠  운영)
        │            │           │                        │        │       │        │
        └── Lead ────┴─ Consulting┴─ Quote/Meeting         └─ Client.stage 축 ───────┘
                     (leadId로 계약前 생성)                     ▲
                                                    HospitalProfile (SoT) — 모든 단계가 참조/기록
                                                    Carry-Forward Contract — 재입력 0 (§3.3)
```

- **단일 상태 축:** 리드 4단계 + 거래처 5단계 = 사장님 8단계에 1:1. 계약 전환이 두 축을 잇는 유일한 관문.
- **SoT 중심:** `HospitalProfile`이 진료과·원장·강점·금지표현·톤·경쟁병원을 보유 → 컨설팅·키워드·GEO·콘텐츠·검수가 모두 여기서 근거를 읽음.
- **인계 계약:** 아래 §3.3의 필드 매트릭스가 "생성→재사용" 규칙을 강제.

### 3.2 워크플로우 단계별 상세 설계
각 단계 = **입력(전단계서 인계) · 도구 · 출력(저장+연결) · 다음단계 전환(트리거) · 정직성 티어**.

**1. 상담문의** — 입력: (없음/외부문의) · 도구: 리드 폼(`/leads`) · 출력: `Lead`(병원명·연락처·지역·URL·동의) · 전환: `CONTACTING`→…수동 · 티어: REAL.

**2. 자료수집·컨설팅보고서** — 입력: Lead의 병원명·URL·지역 · 도구: 무료 SEO진단(엔진 실측) + 컨설팅 생성(Claude) · 출력: `Lead.audit*` + **`ConsultingReport(leadId)`**(키워드·경쟁·상권·요약) · 전환: 보고서 완료→`MEETING` · 티어: 진단 REAL / 컨설팅 AI(🟡검색량 데모 가능). **[갭: leadId 추가 필요]**

**3. 보고서전달·미팅** — 입력: 컨설팅 보고서 · 도구: 견적 3종(`Quote`)+회의록+포털전달 · 출력: `Quote(leadId)`, `Meeting` · 전환: 제안발송→`PROPOSAL` · 티어: REAL(전사) / 미팅 전사 🟡.

**4. 계약** — 입력: 병원명·갑정보(거래처/컨설팅서 인계)·견적항목 · 도구: 계약서+원격서명(`/sign`) · 출력: `Contract`, `ContractProduct`(서명 시 업무 자동생성) · 전환: **계약전환→거래처 생성 + `Client.stage=ONBOARDING`** · 티어: REAL. **[인계: 양방향 완료]**

**5. 담당자배정** — 입력: Lead의 모든 정보(name·연락처·지역·진료과·견적) · 도구: `convertLeadToClient`(원자적) · 출력: `Client`(+`HospitalProfile` 시드)·`assignedMarketerId`·`AccessScope`·`ConsultingReport` 승계 · 전환: 배정완료→`KEYWORD` · 티어: REAL. **[갭: 컨설팅 leadId→clientId 승계]**

**6. 키워드수집** — 입력: 컨설팅 산출 키워드 · 도구: 키워드관리+검색량(네이버)+CEP파인더 · 출력: `Keyword`(검색량·연관어·targetRank) · 전환: 키워드 확정→`GEO` · 티어: 저장 REAL / 검색량·연관어 🟡네이버.

**7. GEO측정** — 입력: 확정 키워드·병원 프로파일 · 도구: GEO모니터링(질문세트→4AI 관측)+GEO Studio · 출력: `GeoQuestion`/`GeoAnswerRecord`(인용율)·`GeoContentDiagnosis` · 전환: 질문승인·측정완료→`CONTENT` · 티어: 수동 REAL / 자동 🔵AI. **[인계: GEO질문→ContentPlan(`answerPlanId`) 활성화]**

**8. 콘텐츠생성** — 입력: 키워드·GEO진단·병원 금지표현 · 도구: 원고/이미지/디자인 스튜디오+답변페이지+의료법검수 · 출력: `ContentPlan`(→검수→승인→발행)·`AiContent` · 전환: 발행→`LIVE`(운영) · 티어: 생성 🟡AI / 검수 REAL / 포털컨펌 REAL.

**운영·보고·정산** — `LIVE`에서 월보장 순위·성과 추적(인사이트)·월간 보고서·청구/정산. 피드백→업셀(§5.4).

### 3.4 현재 갭 → 전환 로드맵 (Phased)

- **Phase 1 — 파이프라인 백본 ✅(완료·배포됨):** `Client.stage`(ONBOARDING→…→LIVE) + 상태머신 + 전환액션 + 계약전환 시 초기단계 + 목록·상세 뱃지·스테퍼.
- **Phase 2 — 데이터 인계:** ✅계약 이음새 양방향 인계(완료). 🔶 `ConsultingReport.leadId` 추가(계약前 컨설팅 + 전환 승계). 🔶 확정 키워드→GEO·콘텐츠 인계.
- **Phase 3 — 가시성:** 거래처 **여정 타임라인**(상담→…→콘텐츠 한 화면) + 거래처 **칸반 보드**(단계별) + GEO 7라우트 통합 워크스페이스 진입점.
- **Phase 4 — 자동 전환:** 이벤트 기반 단계 자동제안(계약체결→배정, 키워드확정→키워드완료, GEO승인→GEO, 발행→운영) + `answerPlanId` 7→8 브리지 + `Product.defaultTasks/Survey/Report` 하류 자동생성 배선.
- **Phase 5 — 실측 활성·신선도:** 네이버/구글/AI 키 실측 전환(현장), 크론(`CRON_SECRET`) 상시화, 온보딩 SLA(3일) 트래커, 진행률 데이터기반 교정(제목매칭 제거).

### 3.5 목표 화면 구조(네비 재편안, 선택)
현재 네비는 *기능별*(영업·계약/기획·분석/제작·검수). 목표는 **파이프라인 우선 + 기능 보조**:
- **파이프라인**(신규): 거래처 보드(단계별) · 거래처 여정.
- 영업(리드·컨설팅·견적·계약) / 실행(키워드·GEO·콘텐츠·검수·발행) / 운영(인사이트·보고·정산) / 협업 / 관리.
